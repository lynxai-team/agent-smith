# Tool Abstraction

Agent Smith unifies all callable units — agents, actions, workflows, commands, and adaptaters — under a single `ToolSpec` interface. This allows the agent's inference loop to execute any feature type interchangeably, regardless of whether it is defined as YAML, JavaScript, or Python.

## The ToolSpec Interface

Defined in `@agent-smith/types`, the `ToolSpec` interface extends `ToolDefSpec`:

```typescript
interface ToolDefSpec {
    name: string;
    description: string;
    arguments: {
        [key: string]: {
            description: string;
            type?: string;
            required?: boolean;
        };
    };
}

interface ToolSpec extends ToolDefSpec {
    type: string;
    parallelCalls: boolean;
    execute: <O = any>(args: {
        [key: string]: any
    } & { toolOptions?: AgentInferenceOptions } | undefined
    ) => Promise<O>;
    canRun?: (tool: ToolCallSpec) => Promise<boolean>;
}
```

### Fields

- **`name`** — Unique identifier for the tool, used in the `tool` and `aliases` tables.
- **`description`** — Natural language description of what the tool does. Used as context in LLM prompts.
- **`arguments`** — Schema defining required and optional parameters with descriptions. The LLM uses this to construct valid tool call payloads.
- **`type`** — The feature category: `agent`, `task`, `action`, or `workflow`. Stored in the `tool.type` column.
- **`parallelCalls`** — Whether multiple invocations of this tool can execute concurrently.
- **`execute`** — Async function that performs the tool's work. Receives parsed arguments and optional `AgentInferenceOptions`.
- **`canRun`** — Optional guard function that receives a `ToolCallSpec` and returns whether the tool should execute (e.g., checking if required arguments are present).

## Multi-Language Support

Tools can be implemented in three formats:

### JavaScript ESM Modules

```javascript
// actions/weather.js
async function action(params, options) {
    const { location } = params[0] || {};
    return `Weather in ${location}: Sunny, 72°F`;
}

export { action };
```

The execution engine loads these via dynamic import and calls the exported `action` function.

### Python Scripts

Python actions are executed through a subprocess call with the Python interpreter, passing parameters as JSON.

### YAML / Shell Commands

YAML-defined actions specify shell commands or inline scripts:

```yaml
name: list_files
description: List files in a directory
arguments:
  path:
    description: Directory to list
    required: true
script: ls -la {path}
```

## Tool Registration

During feature discovery, `extractToolDoc()` and `extractAgentToolDocAndVariables()` generate tool specifications from feature files. These are stored in the `tool` table as JSON strings in the `spec` column:

```sql
INSERT INTO tool (name, spec, type) VALUES (?, ?, ?);
```

The `type` column indicates the source feature type (`agent`, `task`, `action`, or `workflow`).

## Execution Flow

When the agent's inference loop receives a tool call from the LLM:

1. The `ToolCallSpec` (containing `id`, `name`, and `arguments`) is matched against registered tools.
2. If `canRun()` is defined, it is called to check execution permissions.
3. The `execute()` function is invoked with the parsed arguments.
4. Results are fed back into the conversation history as a `ToolTurn`.
5. The LLM receives the tool output and decides whether to call more tools or produce a final response.
